# Refactoring UI：EtherCAT 配置查阅工具的设计应用笔记

阅读日期：2026-10-24。来源为用户指定的 [Refactoring UI 中文译站](https://shallowhawk.github.io/refactoring-ui-zh/)，原书作者 Adam Wathan、Steve Schoger；该站为非官方翻译。

已逐章读取以下 9 个章节页面的完整 HTML 正文。本文是针对本工具的归纳和设计决策，不是原文摘录，不复制书中插图；未将全部插图逐张放大审查。以下具体尺寸和组件方案属于项目应用建议，不应误认为书中的强制标准。视觉基调同时遵循用户提供的 Cap 参考：近白画布、蓝色交互重点、细灰分隔、克制的层次。

## 01 · 从零开始

来源：[从零开始](https://shallowhawk.github.io/refactoring-ui-zh/starting-from-scratch/)

**阅读要点：** 从一个真实功能确定内容与操作，再决定应用外壳；先解决灰度下的结构，短周期实现；限制字号、颜色、间距等设计选项，形成一致体系。

**本工具的应用：**

- 首先做通“输入配置名 → 找到条目 → 读懂含义 → 查看对应字段 → 修改示例参数并理解计算”的完整路径，以一项真实配置验证布局。
- 搜索结果使用实际的英文宏名、中文解释和路径，不用短占位文案掩盖长名称问题。
- 中性无衬线字体、专业直接的措辞、小范围蓝色强调共同建立工程工具的个性。普通控件使用克制圆角，胶囊形保留给筛选或模式切换。
- 先统一 token，再组合组件；不为每个面板临时添加一种蓝色、字号或圆角。
- 页面出现的搜索、关联跳转、计算和复制操作必须真实可用；待做功能不伪装成可用入口。

**界面检查：** 去掉品牌颜色后，用户仍能找到搜索、当前条目和计算结果；以真实长内容完成首个闭环。

## 02 · 层级就是一切

来源：[层级就是一切](https://shallowhawk.github.io/refactoring-ui-zh/hierarchy-is-everything/)

**阅读要点：** 用字重、颜色和弱化周围内容建立层级，不把所有工作交给字号；操作的重要性决定其视觉强度；技术查阅场景中字段标签本身可能就是查找目标。

**本工具的应用：**

- 条目详情的第一层是配置标识和一句话解释；第二层是适用条件、取值规则与关联；来源时间等元数据位于更低层级。
- 搜索结果突出配置名，中文说明次之，来源和路径再弱一级。宏名和字段名是用户扫读目标，不能因为“标签通常应弱化”而隐藏它们。
- 当前侧栏项使用浅蓝底、较深文字和明确标记；其余导航降低视觉重量，避免整列高饱和色与正文争夺注意力。
- 同一区域只保留一个最强操作。复制字段、查看来源、重置示例采用轻量按钮或文本链接。
- 语义标题保持正确层级，视觉上的栏目标题无需被放大成营销标题。辅助文字通过色阶区分，避免低于可读字号。

**界面检查：** 首屏能迅速回答“当前查的是什么、是什么意思、下一步能做什么”；图标和大量按钮不能压过配置内容。

## 03 · 布局与间距

来源：[布局与间距](https://shallowhawk.github.io/refactoring-ui-zh/layout-and-spacing/)

**阅读要点：** 从充足留白逐步收敛；用有明显差异的尺寸阶梯；元素只占内容所需空间，侧栏不必按屏幕比例增长；组间距离应大于组内距离。

**本工具的应用：**

- 使用稳定宽度的目录栏与弹性主区；关联栏仅在剩余宽度足够时并列，窄屏下移入正文或可展开区域，避免三栏同时压缩文字。
- 正文解释限制适合中文阅读的行宽；宽映射表、XML 和计算步骤可使用独立更宽区域，避免为一张表拉长所有段落。
- 采用有限间距档位，例如 4、8、12、16、24、32、48px；不把“4px 的任意倍数”误当作有效约束。
- 标签与其输入框紧邻，两个参数组之间明显留白；公式、代入过程、结果保持同组关系，错误提示紧邻对应输入。
- 搜索结果可以刻意紧凑，详细解释需要较多阅读空间。密度服务查阅任务，不以填满一屏为目标。

**界面检查：** 在桌面与约 400px 的窄屏检查长字段、表格和公式；不依赖缩小字号解决溢出，表格需要横向滚动时仅让表格自身滚动。

## 04 · 文字设计

来源：[文字设计](https://shallowhawk.github.io/refactoring-ui-zh/designing-text/)

**阅读要点：** 选择有限的字号阶梯和适合小字号的字体；控制行长并按文本密度调整行高；混合字号按基线对齐；列表里的链接不必全部成为蓝色；数据对齐服务比较。

**本工具的应用：**

- 中文正文与解释采用清晰的系统无衬线字体栈；宏名、XML 路径、十六进制数、公式代码使用等宽字体，不给整篇解释套等宽字体。
- 以 14、16、20、24px 等有限档位组织内容，12px 仅用于非关键短元数据；用 rem 或明确 token 避免嵌套 em 导致字号漂移。
- 技术解释左对齐，正文约 1.6–1.75 行高；标题更紧凑。中文行宽通过实际阅读检查，不机械套用英文字符数。
- 搜索列表的整行可点击，默认用深色标题、明确悬停和焦点状态；正文中的跨引用用蓝色及下划线等可识别样式。
- 数值列右对齐并使用等宽数字，地址和标识列按查找需求对齐；结果与单位基线一致。长路径允许合理换行或局部滚动。
- 字距用于必要的英文短标签，不把 Cap 的大写眉题字距应用到中文长句或精确标识符。

**界面检查：** 长中文解释、全大写宏名、十六进制值和多行公式均可读；缩放后没有关键文字被截断。

## 05 · 色彩的运用

来源：[色彩的运用](https://shallowhawk.github.io/refactoring-ui-zh/working-with-color/)

**阅读要点：** 建立灰色、品牌色与语义色的固定色阶；在真实使用场景中校准色阶；浅色底配深色字可以兼顾层级与对比；颜色只能辅助传达含义。

**本工具的应用：**

- 以 Cap 的 `#fcfcfc` 画布、`#202020` 正文、`#2563eb` 主操作为起点，建立背景、边框、正文、次要文字、交互、焦点的语义 token。
- 青蓝、紫色、橙色不任意扩散到来源标签或装饰。主要内容保持中性，蓝色集中表达选中、可操作和关键结果。
- 来源类型直接写 SSC、XLSX、ESI；引用关系直接写“对应字段”“依赖”“影响”。不要求用户记住三个来源各自的颜色。
- 计算错误、适用性提醒、成功反馈使用文字与图标并辅以语义色；警告浅底深字，避免大块饱和色抢走正文注意力。
- 对比度根据最终前景/背景组合实测。Cap 的浅灰辅助色不能直接套给所有小字；非颜色线索同时覆盖选中、错误和焦点。
- 原书中的色彩表示方法作为调色思路，不视为当代浏览器色彩能力的完整说明。

**界面检查：** 普通正文目标对比度至少 4.5:1；高亮、筛选、校验提示在灰度观看时仍能区分。标准阈值最终以项目的无障碍验收依据为准。

## 06 · 营造层次感

来源：[营造层次感](https://shallowhawk.github.io/refactoring-ui-zh/creating-depth/)

**阅读要点：** 阴影应表达元素所在高度和交互状态；固定少数高度档位；平面风格也能通过色阶、分层和有限重叠传达前后关系。

**本工具的应用：**

- 常驻目录、条目正文、参数表使用平面结构，不给每段内容套带阴影卡片。
- 搜索建议、来源弹层和移动端导航在确实覆盖内容时使用适量阴影；层级高于所在页面，遮罩与焦点行为保持一致。
- 计算输入使用浅灰承载区，结果用轻量浅蓝区或蓝色数值，靠对比传达作用，避免模拟实体仪器的重度光泽。
- 将阴影与 z-index 定为少数清晰角色：页面、浮层、对话框。状态切换保持布局稳定，不靠 hover 抬升导致内容跳动。

**界面检查：** 用户能看出当前打开的浮层及关闭方式；关系和计算信息依然是视觉重点，没有多重阴影包围内容。

## 07 · 图片的运用

来源：[图片的运用](https://shallowhawk.github.io/refactoring-ui-zh/working-with-images/)

**阅读要点：** 图片必须与实际用途和展示尺寸匹配；密集截图不应缩成不可读缩略图；小图标和 favicon 需要针对目标尺寸处理；图片上的文字需稳定对比。

**本工具的应用：**

- 工具以文字、表格、关系和公式为核心，不为填补空白加入工程照片或大幅装饰图。
- 若展示 SSC 操作位置，优先裁剪到相关设置区域，附文字步骤和版本，提供看原图入口；关键步骤不只写在截图内。
- 关系图使用清晰文本与箭头，确保节点在实际显示尺寸下可读；重要关系同时存在于可访问的文字列表。
- 导航图标保持原始设计尺度附近，通常 16–20px，笔画风格统一；应用标识与 favicon 使用专门适合小尺寸的简化图形。
- XML、对象字典表和计算结果应以可复制的文本呈现，不用截图替代。

**界面检查：** 在 100% 页面缩放下能读懂截图中需要识别的位置；在浏览器标签栏检查 favicon 的实际辨识度。

## 08 · 收尾打磨

来源：[收尾打磨](https://shallowhawk.github.io/refactoring-ui-zh/finishing-touches/)

**阅读要点：** 打磨已有元素即可提升完成度；小范围强调色能建立重点；空状态要指导下一步；通过间距和背景减少过量边框；组件形式围绕内容设计。

**本工具的应用：**

- 当前目录项、搜索命中和计算结果可用短蓝线或浅蓝块强调，避免把所有卡片描成蓝框。
- 搜索无结果时保留查询内容，说明可尝试英文名、中文关键词或索引，并提供清除筛选和示例查询。没有关联或计算内容时给出准确说明，不显示空白容器。
- 参数非法时将原因、有效范围和单位放在字段附近；复制后有短暂可感知反馈；链接失效或参考内容缺失有明确状态。
- 相邻组优先用间距区分，完整表格保留有用行分隔；不同时叠加深背景、粗边框与阴影。
- 映射信息可以把“来源名称 + 具体位置 + 说明”组织成便于扫读的行，而非机械拆成大量窄列。关系项加入方向与含义，避免只堆可点击标签。
- 背景装饰和渐变不是此工具的默认选择；只有能帮助分区或理解时才考虑添加。

**界面检查：** 覆盖首次进入、无结果、多个命中、无关联、错误输入、复制反馈以及超长名称；每个状态都给出清楚结果或下一步。

## 09 · 持续进阶

来源：[持续进阶](https://shallowhawk.github.io/refactoring-ui-zh/leveling-up/)

**阅读要点：** 观察参考设计中自己不会主动做出的决定；通过亲手重建和差异分析，发现实际影响质感的细节。

**本工具的应用：**

- 把 Cap 参考拆成可验证属性：画布、蓝色使用比例、字重、边界、控件密度；沿用它的视觉规律，不照搬营销内容结构。
- 以真实浏览器截图复核首屏、长条目、复杂关联和计算状态。每轮先记录最影响查阅的一处差异，再调整并复验。
- 对照“找到字段需要几步”“对应关系能否一眼识别”“计算依据是否可追溯”判断设计改动，而不只看单张静态截图是否漂亮。
- 将复验中确认有效的模式回收到 token 和公共组件，避免只在单页打补丁。

**界面检查：** 最终截图与可操作页面共同审查；保留关键场景和修正记录，不能用静态原型替代实际交互验收。

## 综合落实顺序

1. 用真实条目实现搜索、解释、跨来源映射、关联和计算闭环。
2. 先审查灰度层级、分组和文字，再应用 Cap 的颜色与形状规则。
3. 以稳定侧栏、适度行宽和宽屏关联区组织信息；窄屏调整结构，不挤压全部栏位。
4. 完成查询无结果、参数错误、缺失来源、复制反馈等状态，保持键盘操作与焦点可见。
5. 在实际浏览器中检查长内容、数字单位、对比度、窄屏、缩放和应用图标，将发现的问题修正后再交付。

这些笔记用于指导本项目实现；具体页面结构和数值仍需结合真实资料量、协议内容与浏览器验证结果确定。
